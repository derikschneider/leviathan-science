# CLAUDE.md — Working Rules

General working rules for Derik's projects — kept identical across repos (`vite-lit-1`, `workshop`, this one, `toolkit`, and `derik-workspace`) so they travel to whichever machine/repo you're working from. If these get updated, update all copies together.

## What this repo is

`leviathan-science` (GitHub: `derikschneider/leviathan-science`) — a font foundry site placeholder. Lit + TypeScript + Vite, deployed via GitHub Pages, **must stay public** (GitHub Pages requires it on the free plan, same constraint as `vite-lit-1`). Currently a minimal scaffold: a Spline 3D viewer embed ("Ghost Leviathan" model) plus commented-out variable-font weight/width slider controls (`--ls-wght`/`--ls-wdth` CSS custom properties) — not yet a built-out site, more a working sketch of the foundry's visual identity direction.

`experiments/hex-hero/` is a standalone single-file prototype (open it directly, no build step) of a hero treatment: a WebGL2 height-field raymarch over a hex lattice, where the cursor carries a raised ring across a flat floor and the wordmark is printed into the tile faces rather than sitting on top of them. All tuning lives in one `CONF` object near the bottom of the file - hex count across the viewport, camera tilt in degrees, side-wall height in px, the ring profile (`r0`/`rise`/`hold`/`fall`, as fractions of viewport width measured out from the cursor), seam and outline widths, and the soft key light. Two things there are deliberate and easy to undo by accident: elevation is expressed in **screen px, not cell units**, so changing hex size does not silently change how high the tiles stand; and the visible honeycomb line is a **drawn outline (`edgePx`) separate from the physical gap (`gapPx`)**, because at the sub-pixel gap the reference uses, the separation alone is far too fine to read as a lattice. The CTA is two layers: the visible plate is painted into the content texture so the ring splits it along hex seams at rest, and hovering the invisible `<a>` hit-region raises the plate's rounded-rect region of the height field as a rigid slab - the side walls are the drop shadow, no second visual button exists. `shots/` holds the iteration history, highest version suffix is current.

## Working Rules
Kept identical across repos (`private`, `vite-lit-1`, `workshop`, `leviathanscience`, `toolkit`) so they travel to whichever machine/repo you're working from. If these get updated, update all copies together.

- Think through the problem first, and read the relevant files in the codebase before proposing or making changes.
- Check in before major changes — lay out the plan and wait for confirmation before executing anything large or hard to reverse.
- Along the way, give a high-level explanation of what changed at each step, not a line-by-line narration.
- Keep every change as small and targeted as possible. Touch as little code as necessary to do the job. No speculative refactors, no scope creep, no unrequested cleanup while in the area — exception: sweeping changes (e.g. deleting an entire project or folder) are fine when explicitly asked for, but scope them exactly to what was requested.
- Never speculate about code that hasn't been opened. If a specific file is referenced, read it before answering. Investigate before making claims about the codebase — no guessing.
- Each project should have a maintained doc describing its architecture end-to-end, kept current as the project changes.
- Verify actual output, not just absence-of-errors — a clean typecheck or a script exiting 0 is not proof of correctness. Check the real result (render it, view the image, spot-check the data) before calling something done, and prefer two independent signals over one when it matters (raw source vs. a summarized fetch, `curl` vs. a browser timeout, and so on).
- Fix real bugs and debt the moment they're found, not after finishing the current task — a fix is cheapest right when it's caught, and deferred debt compounds as fast as new code gets generated.
- When a TODO/open-item note gets resolved (status doc, README, inline comment), update or remove that note in the same session the resolving change lands — don't leave documentation claiming something is still open once the commit history or code shows it's done. A future session trusts these notes without re-verifying against source; a stale one costs that session real time re-litigating something already settled (e.g. `portfolio-next/CLAUDE.md`'s "Known open gaps" list survived three resolving commits before anyone noticed, 2026-07-27).
- **Default to Derik's own taste and brand voice for any UI/visual/design work** — [preferences.md](preferences.md), `brand-voice.md`, and `imagery guidance.md` are the source of truth, not a blank-slate or skill-generated direction. Treat them as a sensibility (typography instincts, tone, animation philosophy) to adapt per project, not a literal skin — `preferences.md` currently documents the personal derikschneider.com site specifically, which is fine as the default lens for now but shouldn't be copy-pasted wholesale onto an unrelated product.
- **New projects, or ones without their own defined visual direction yet, use that default as the goto** until the project has a real direction of its own — defining one is still required, even if it's several candidate directions with acknowledged overlap between them. Don't skip straight to shipping on the default without ever converging on the project's own identity.
- **Once a project has its own established taste** (a `DESIGN.md`, a documented brand system, or clearly coherent existing visual work already in place), that identity wins over the personal default — the default is a fallback starting point, not a permanent override.
- **Design/critique/audit skills (e.g. `impeccable`) execute and enforce quality — they don't originate direction.** Feed them Derik's taste sources above (or a project's own established ones, once it has them) rather than letting a skill's own greenfield discovery process invent an unrelated direction from scratch.
- **Treat "which skill or subagent covers this job" as part of planning itself, not something Derik has to name aloud** — the way a contractor brings the right trade without being asked. When breaking nontrivial work into steps, actively match each job to an existing skill/subagent rather than waiting to be told to invoke `grill-me`, `multi-expert-brief-review`, or similar by name. Custom procedure-style skills built for this workspace should default to auto-invocable (no `disable-model-invocation`) so this actually works — only gate a new one behind manual invocation if there's a specific reason (genuinely risky, or meant as a deliberate manual override), not as a blanket default.
- **If a job has no matching skill, that's a signal to spike/research it, then close the task by turning what was learned into a new skill (or extending an existing one) on the spot** — not as a deferred follow-up someone has to remember to come back for. (`graph-engineering`, built the same session it was discussed, 2026-08-03, is the reference example.)
